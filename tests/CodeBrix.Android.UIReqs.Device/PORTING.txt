ADAPTATIONS (each marked "ANDROID PORT" in the file)
  (1) `using CodeBrix.Platform.UI.Runtime.Skia.Linux.FrameBuffer.Emulated.TestTarget;` ->
      `using CodeBrix.Android.UIReqs.Device.TestTarget;` (host: CodeBrix.Android.UIReqs.TestTarget): the
      emulated frame-buffer head's session/frame types are replaced by the Android ones (Runtime/TestTarget.cs).
  (2) `using SkiaSharp;` -> `using SKColor = CodeBrix.Android.UIReqs.Device.Canvas.PixelColor;` (the canvas
      vocabulary used SKColor only as a colour struct; no Skia in the Android harness - family policy).
      Support/TestImage.cs writes its two-colour PNG with the managed PngCodec instead of an SKCanvas.
  (3) Hosting/TestTargetFixture.cs: LaunchAsync attaches to the running app (the runner script launched it;
      the host declares the orientation) instead of setting up a frame-buffer panel; ShutdownAsync only
      forgets the session; WaitForLayoutAsync compares in pixels (density per XamlRoot); NextFrameAsync
      additionally runs the layout-replay GEOMETRY AUDIT (Runtime/GeometryAudit.cs: every named element's
      native view rectangle = its Core rectangle within 1 px) after each captured frame.
  (4) Hosting/TextEngineBootstrap.cs: a no-op (no Skia text engine; text is native, via the TextBlock handler).
  (5) (none beyond (1)/(2) in Support.)
  (6) FIX: Canvas/ModeColor.cs + CanvasAssert(.ThemeFocus/.Buttons).cs - a colour bucket's representative is
      its MOST FREQUENT exact colour, not the first pixel met (an anti-aliased glyph edge on Android). The
      Platform copy took the same rule at the engine pass (WPE1-5 B7).
  (7) tools/UIReqsFrameCompare: PNG decode/encode through the managed PngCodec (Protocol/PngCodec.cs, linked)
      instead of SkiaSharp; FrameImage.cs stands in for SKBitmap.
  (8) Hosting/VirtualApplication.cs SetContentAsync waits (at most ~1 s) until the new content IsLoaded: Core
      raises Loaded on the next layout tick and an unloaded element is not hit-testable, so a tap sent right
      after "the application shows ..." could fall through to the panel (the AP3a "first-tap race"; AP2-M).

WHAT IS NEW (Android only)
  Shims/        the Reqnroll attribute/context surface and xunit's TestContext as the copied code uses them
                (the device does not run Reqnroll - the host does), and PixelColor.
  Runtime/      StepServer (the TCP step server the host drives), StepCatalog + CucumberExpression (step
                matching: {int} {float} {double} {word} {string} {}, optional text, alternatives), BindingScope
                (context injection + hooks), HostChannel (capture / save-frame requests to the host),
                TestTarget (session: panel, UI thread, Core's InputInjector for touch, frame handshake),
                GeometryAudit, InputTrace (logcat tag UIReqs.Input), HostFrames (FrameArchive/FrameReview
                stubs that forward to the host), AppHost.
  Protocol/     the wire protocol (one JSON line per message, raw frame bytes after a "bytes" header) and the
                managed PNG codec - shared with the host project and the frame-compare tool.
  MainApplication / MainActivity: the scenario app (its XAML application is the copied VirtualApplication;
                full screen, so a screencap is the app window).

KEYBOARD (AP2.5)
  Runtime/TestTarget.cs KeyDown/KeyUp/TypeText dispatch REAL Android KeyEvents to the activity (the path a
  hardware keyboard takes: DispatchKeyEvent -> the window's keyboard input source -> Core). Core's own
  keyboard injection (InputInjector.InjectKeyboardInput) is a NotImplemented stub in the pinned build.

ANDROID-ONLY GROUPS (not copies; AP2.5/AP2.6)
  AndroidFeatures/<Group>/*.feature with their steps in AndroidSteps/ (linked by the host project like the
  copied features): AndroidInput (real MotionEvents and KeyEvents reach Core: pointer events and Tapped on a
  Grid with a Background, right click, wheel, hover, keys on a page, an Alt accelerator, keyboard arrows) and
  AndroidNative (native ScrollViewer scrolling with real drags, ChangeView and the wheel; offsets reported).
  Later lanes (each group's steps in its own AndroidSteps/ file):
  AndroidControls (AP3a, NativeControlsSteps.cs): the native widget types of the sample controls, real
      MotionEvents/KeyEvents on them (exactly one Click / Checked / Toggled; a real finger on the Slider; real keys

      ComboBoxHandler.Enabled on for one scenario; an [AfterScenario] hook turns it off), NumberBox and
      AutoSuggestBox. Its [BeforeTestRun(Order = -100)] hook turns NativeTemplateParts ON for the whole run: the
      copied scenarios that measure Fluent template parts (NormalRectangle, SwitchKnob, HorizontalThumb, ...) find
      stand-ins placed where the native widget draws them (OFF in apps).
  AndroidItems (AP3b, NativeListsSteps.cs): RecyclerView-backed lists - only the visible rows realised, real-finger

      Material forms are OFF for every scenario not tagged @native-overlays (the copied Popups group reads Core's

  AndroidPolicy (AP5, PolicySteps.cs): size classes (real and simulated), the adaptive NavigationView and

ADD-IN GROUPS (AP7-A; copies, like the core groups)
  Source: the same CodeBrix.Platform commit 8272e48e45ac98c91073bd4ede1428c7af86d639, src/UIReqs/Platform.UI.AddIn.<Group>/
  (files only; pristine snapshot ~/ClaudeHome/android-buildout-work/uireqs-source-ap7a/, SOURCE.txt). Groups:
  SkiaSharpViews, Svg, Graphics2DSK, CommandBar, FlexPanel, WebView, MediaPlayer, Graphics3DGL.
    Features/<Group>/*.feature                 -> Scenarios/Features/<Group>/        VERBATIM
    Steps/**, Support/**, Registration.cs      -> Scenarios/AddIns/<Group>/          verbatim except (a)-(d)
    Assets/** (artwork, pages, clips)          -> inlined by (b)
  The add-in assemblies the scenarios need come in through Directory.Build.props (CodeBrixAndroidInRepoAddIns: each
  add-in's Core and its CodeBrix.Android add-in project). Runtime/AddInScope.cs scopes an add-in group's steps and
  hooks to its own feature folder (namespace CodeBrix.Platform.UI.AddIn.<Group>.* <-> Features/<Group>/), as each
  group is its own test assembly on the Platform: two groups may define the same step text ("... is invalidated").
  The project allows unsafe code for the Graphics3DGL fixtures (vertex-attribute offsets as raw pointers), as the
  Platform's Graphics3DGL UIReqs project does.
  Adaptations (each marked "ANDROID PORT (x)" in the file):
  (a) warnings-as-errors: a null-forgiving `!` where the device's ScenarioContext shim is NRT-annotated
      (SkiaSharpViews), a CA2255 pragma around the module initializers of Registration.cs (Svg, CommandBar).
  (b) an APK has no folder beside its assemblies: the Assets/ files are embedded as text / base64 in the support
      class that used to read them and written to Path.GetTempPath() on first use (CommandBar DemoIcons, WebView
      local page, MediaPlayer clips).
  (c) Registration.cs bodies of WebView and MediaPlayer are empty: the Linux engines they registered (WPE WebKit,
      LibVLC) do not exist on Android; the Android add-ins register their engines from their own module initializers.
  (d) prerequisite probes: WebView checks the device's system WebView package instead of three Linux libraries;
      MediaPlayer has no native library to preload (Media3 is managed + Java); Graphics3DGL probes libEGL.so
      (the Android system library) instead of Debian's libEGL.so.1.

SINGLE-SESSION ISOLATION (AP7-M)
    Run as ONE app session (android-uireqs-run.sh --group all), two leaks crossed group boundaries; per-group runs
    (a fresh app per group) never showed them. Two Android-only hooks keep every scenario's start state:
    - (AP7-M, REMOVED at AP1.9) AndroidSteps/FrameworkBrushGuard.cs put back the colour of the SHARED framework
      brush AccentFillColorDefaultBrush after Core's ProgressBar Paused / Error ColorAnimation had animated it in
      place (FIXLIST [AP7-M]). Pin 1.0.268.12 fixes it in Core (WPE1-1 C0g: an animation clones a shared brush in
      its target path; WPE1-5 I: the Setter twin), fenced by the copied Range/ProgressBar scenario "A paused
      ProgressBar that goes away leaves the accent colour as it was"; the guard is gone.
    - AndroidSteps/SoftKeyboardHooks.cs: a scenario that typed through a native field (the AutoSuggestBox real
      keyboard scenario, a Material picker's keyboard input) left the soft keyboard up; in landscape it covered the
      bottom of the next WebView scenarios' panel. The hook hides it after every scenario. The Material pickers
      themselves now hide the keyboard their text input raised when their dialog closes
      (Handlers/Composed/MaterialPickers.HideKeyboardAfterDialog), fenced by "the soft keyboard is not showing" in
      the three AndroidComposed picker scenarios.
    - AndroidSteps/PolicySteps.cs PolicyHooks.Use_the_harness_policy runs at BeforeTestRun Order 5 (was 50): before the
      copied ThemeColors.RegisterAsync (Order 10) reads "Accent" once per run. At 50, a run whose theme bridge had
      already written the Material palette at start-up registered the Material primary as "Accent" (a start-up race).
