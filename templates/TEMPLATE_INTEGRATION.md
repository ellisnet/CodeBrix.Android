# Android head for the CodeBrix.Platform application template

This folder holds the **Android head** of the CodeBrix.Platform application template: the files a
new application gets when its author picks "Android" as one of its heads. The template itself lives
outside this repository (CodeBrix.Develop's `src/templates/TemplateApp.zip`, the same archive as
CodeBrix.Platform's `templates/TemplateApp.zip`, generated by `ApplicationTemplate` in
CodeBrix.Develop, and mirrored by the `codebrix-create-new-application` skill). Nothing here changes
those; this document lists exactly what they need, for the maintainer to apply.

## The files

```
templates/AndroidHead/src/
  TemplateApp.Android/
    TemplateApp.Android.csproj   the head project (net10.0-android36.1, SupportedOSPlatformVersion 33, Exe)
    MainApplication.cs           [Application] MainApplication : CodeBrixApplication, CreateApp() => new App()
    MainActivity.cs              [Activity] MainActivity : CodeBrixActivity (launcher, Material 3 theme,
                                 ConfigurationChanges = CodeBrixActivity.HandledConfigurationChanges)
    AndroidManifest.xml          the application element (label); no permissions
  TemplateApp.Core/
    TemplateApp.Core.csproj      the .Core project with TWO target frameworks, used INSTEAD of the archive's
                                 net10.0-only one when the Android head is selected
```

The token is the archive's existing one, `TemplateApp`, replaced in paths and file contents exactly as
the generator replaces it today. No other token is used. It appears in: the head folder and project
name, the `ApplicationId` (`com.companyname.TemplateApp`) and `ApplicationTitle`, the `.UI.projitems`
import and the `.Core` project reference, the `namespace` of the two classes, the activity `Label`, and
the manifest's `android:label`.

The head has no `Program.cs`: Android starts the app through `MainApplication` and `MainActivity`.
The shared `App.xaml.cs` runs unchanged (`OnLaunched`, `Window`, `Frame.Navigate`); its
`InitializeLogging()` is only called by the desktop heads' `Program.Main` (CodeBrixApplication sets
up logging to logcat itself).

## What CodeBrix.Develop's template needs

1. **The archive** (`TemplateApp.zip`): add `TemplateApp/src/TemplateApp.Android/` with the four
   files above, and add the Android variant of the Core project, for example as
   `TemplateApp/src/TemplateApp.Core/TemplateApp.Core.Android.csproj.template` (any name the
   generator does not extract as-is).
2. **The head list** (`PlatformHead` / `PlatformHeadInfo.All`): a seventh head, offered last.

   | Field | Value |
   |---|---|
   | Head | `Android` |
   | DisplayName | `Android` |
   | ProjectSuffix | `Android` |
   | PackageId | `CodeBrix.Android.ApacheLicenseForever` |
   | BootstrapCall | none - the head has no Program.cs (code that writes `Program.cs` from BootstrapCall must skip it) |
   | TargetFramework | `net10.0-android36.1` |

   Adding it to `PlatformHeadInfo.All` also makes `Android` a reserved library suffix
   (`GetLibrarySuffixError` checks every head suffix) and lets `IsUnderUnselectedHead` and
   `PruneUnselectedHeadProjects` drop the folder and the `.slnx` line when Android is not selected.
3. **The `.slnx` line**, after the WinWpfSkia line:
   `<Project Path="src/TemplateApp.Android/TemplateApp.Android.csproj" />`
4. **The Core project, only when Android is selected**: write the two-target-framework
   `TemplateApp.Core.csproj` of this folder in place of the archive's one. When Android is NOT
   selected keep the archive's net10.0-only project: a two-framework Core needs the .NET "android"
   workload on every machine that builds the solution (error NETSDK1147 without it). The Android
   variant keeps every package of the net10.0 variant, moves `CodeBrix.Platform.ApacheLicenseForever`
   into a `net10.0`-only ItemGroup (the desktop package must never reach the Android app), and adds
   `CodeBrix.Android.ApacheLicenseForever` in a `net10.0-android36.1`-only ItemGroup.
5. **The font swap** (`FontSwap.Apply`): the Android variant of the Core project carries the Open Sans
   package reference exactly as the net10.0 one does, so the Roboto swap must be applied to it too.
   The head files contain no font reference.
6. **Package versions**: the head and the Core carry `CodeBrix.Android.ApacheLicenseForever` with
   `Version="*"` in this repository (no version is published yet). When the files go into the
   archive, write the published version there; `ApplicationPackageVersionUpdater` then moves it to the
   latest release like every other reference. The updater (and `PackageReferenceReader`) must read and
   rewrite a PackageReference that sits inside a conditional ItemGroup (the Core's two framework-specific
   groups).
7. **Name validation when Android is selected**: the application name becomes part of the Android
   package name (`com.companyname.<Name>`), whose dot-separated segments must each start with a letter
   and must not be a Java keyword (`int`, `new`, `package`, ...). The generator accepts a segment that
   starts with an underscore; either refuse such names when Android is selected, or derive the
   `ApplicationId` separately.
8. **Machine requirements** (for the dialog's help text): the .NET 10 SDK "android" workload and the
   Android SDK. Android 13 (API 33) is the minimum supported version. Debugging: name no debugger as
   a requirement; CodeBrix.Develop debugs .NET 11 Android apps, and a .NET 10 Android app is debugged
   the way .NET 10 Android apps are debugged today.

The head project deliberately does NOT set `<RootNamespace>`, like every other head (sharing the Core's
root namespace makes the XAML source generator emit a colliding `GlobalStaticResources` type). Its
default root namespace is `<Name>.Android`; code in `namespace <Name>` that wants a Mono.Android type
therefore uses a `using Android.*;` directive (as the two classes do) or `global::Android.*`, never a
bare `Android.` prefix.

## What the codebrix-create-new-application skill needs

- **Step 1 (interview)**, item 3: a seventh head, "Android", offered after Windows WPF-Skia; the default
  "all" stays the six desktop heads unless the user names Android (it needs the android workload).
- **Step 2 (validate)**: `Android` is a head suffix, so it is not a valid library suffix; with Android
  selected, the application-name rule of item 7 above.
- **Step 3 (versions)**: resolve `CodeBrix.Android.ApacheLicenseForever` too when Android is selected.
- **Step 4 (structure)**: `src/{Name}.Android/` with the four files of this folder (token `TemplateApp`
  -> `{Name}`); the `.slnx` line of item 3 above.
- **Step 4b (Core csproj)**: with Android selected, the two-target-framework form of
  `templates/AndroidHead/src/TemplateApp.Core/TemplateApp.Core.csproj`.
- **Step 5 (heads)**: a row `Android | Android | CodeBrix.Android.ApacheLicenseForever | (none: MainApplication +
  MainActivity) | net10.0-android36.1`, and the four files instead of csproj + Program.cs.
- **Step 7 (build)**: `dotnet build {Name}.slnx` needs the android workload when Android is selected. To run
  on a device or emulator: `dotnet build src/{Name}.Android -t:Install` (Debug builds use fast deployment;
  never `adb install` a Debug APK), then start it from the launcher; a Release build writes an installable
  `.apk`.

## Proof

The instantiation that the AP9-1 work package ran (the steps above applied by a script to a copy of the
archive, the LinuxX11 and Android heads selected, built against the locally packed CodeBrix.Android
packages from an isolated package folder) is recorded in the work package's report; the on-device run
of such an app is part of the next work package.
